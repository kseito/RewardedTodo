# アーキテクチャ上の意思決定をADRとして記録する

## 背景と課題

設計判断はPRの説明文・レビューコメント・コード内コメントに散在している。時間が経つと「なぜそうしたか」が失われ、同じ論点が再指摘されたり、根拠を確認できないまま実装が書き換えられたりする。

`docs/review-policy.md` は「人の目を向けるべき4点」の一つに設計・セキュリティの判断を挙げており、その判断結果をどこに残すかを決める必要があった。

## 検討した選択肢

* PRの説明文とコード内コメントに残す（現状維持）
* GitHub Wiki や Notion などリポジトリ外のドキュメントツールに残す
* リポジトリ内の `docs/adr/` に1決定1ファイルで記録する

## 決定

採用: 「リポジトリ内の `docs/adr/` に1決定1ファイルで記録する」。書式・命名・雛形は `CLAUDE.md` の記載に従う。

- コードと同じPRでレビューでき、チェックアウトすれば常に手元にある。リポジトリ外のドキュメントツールは、コードの変更と同期が取れずに陳腐化しやすい。
- PRの説明文は「その変更で何をしたか」の記録であって、決定が今も有効かを示さない。覆された判断と生きている判断を後から区別できない。
- 1決定1ファイルの連番にすることで、決定を安定したIDで参照でき（コードコメントやレビューから `docs/adr/0001-...` と指せる）、追記による肥大化も避けられる。

記録する対象は、後から根拠を問われる判断・覆すのに労力がかかる判断（レイヤー構成、DI構成、永続化方式、CI/テスト基盤の運用など）に限る。命名やフォーマットのように機械的に矯正できるものは対象外とする。

### 結果・トレードオフ

- 受け入れたコスト: 設計判断のたびに文書を書く手間が増える。これを抑えるため、対象を上記の範囲に限定し、1本あたり1画面に収まる分量を目安とする。
- ADRは決定時点のスナップショットであり、現状の設計ドキュメントではない。「今どうなっているか」は `docs/domain-model.md` や `docs/module-dependency.md` 側に書き、ADRは「なぜそう決めたか」に徹する。
- 決定を覆す場合は既存ADRの本文を書き換えず、新しいADRを追加し、元のADRの `status` を `superseded by ADR-NNNN` に変更する。
- 再評価が必要になる条件: ADRが増えて一覧性が落ちた場合は、`docs/adr/README.md` に索引を追加することを検討する。
