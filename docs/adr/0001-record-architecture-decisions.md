# ADR-0001: アーキテクチャ上の意思決定をADRとして記録する

| 項目 | 内容 |
|------|------|
| ステータス | Accepted |
| 決定日 | 2026-09-12 |
| 関連 | `docs/review-policy.md` / `docs/adr/_template.md` |

## 背景

本プロジェクトの設計判断は、PRの説明文・レビューコメント・コード内コメントに散在している。時間が経つと「なぜそうしたか」が失われ、同じ論点が再指摘されたり、根拠を確認できないまま実装が書き換えられたりする。

`docs/review-policy.md` では「設計判断は `docs/adr/` にADRとして記録する」方針を掲げているが、採番・命名・ステータスといった運用ルールが定義されておらず、実際に記録されたADRも1本に留まっていた。

## 決定

アーキテクチャ上の意思決定は、リポジトリ内の `docs/adr/` に連番のMarkdownファイルとして記録する。運用ルールは以下のとおり。

- **置き場所・命名**: `docs/adr/NNNN-kebab-case-summary.md`（`NNNN` は0001から始まる4桁の連番、要約は英小文字ケバブケース）
- **雛形**: `docs/adr/_template.md` をコピーして書く。見出し構成（背景 / 決定 / 理由 / 結果・トレードオフ）は変更しない
- **ステータス**: `Proposed`（議論中）→ `Accepted`（採用）。後続ADRで覆した場合は元のADRを `Superseded` にし、関連欄で新しいADRを指す。**既存ADRの本文は書き換えず、新しいADRを追加して上書きする**
- **記録する対象**: 後から根拠を問われる判断、覆すのに労力がかかる判断（レイヤー構成、DI構成、永続化方式、CI/テスト基盤の運用など）。命名やフォーマットのような機械的に矯正できるものは対象外
- **参照**: 判断が実際に効いているコードには、コメントから該当ADRのパスを書いて辿れるようにする

## 理由

- **リポジトリに同梱する**ため、コードと同じPRでレビューでき、チェックアウトすれば常に手元にある。GitHub Wiki や外部ドキュメントツール（Notion等）は、コードの変更と同期が取れずに陳腐化しやすい。
- **PRの説明文だけでは不十分**。PRは「その変更で何をしたか」の記録であって、決定の現在の有効性を示さない。覆された判断と生きている判断を後から区別できない。
- **1決定1ファイルの連番**にすることで、決定を安定したIDで参照でき（コードコメントやレビューから `docs/adr/0002-...` と指せる）、追記による肥大化も避けられる。
- 形式はMichael Nygard の Architecture Decision Record を踏襲する。本プロジェクトでは日本語で書き、見出しは既存の `_template.md` に合わせる。

## 結果・トレードオフ

- 受け入れたコスト: 設計判断のたびに文書を書く手間が増える。これを抑えるため、対象を「後から根拠を問われる判断」に限定し、1本あたり1画面に収まる分量を目安とする。
- ADRは**決定時点のスナップショット**であり、現状の設計ドキュメントではない。「今どうなっているか」は `docs/domain-model.md` や `docs/module-dependency.md` 側に書き、ADRは「なぜそう決めたか」に徹する。
- **再評価が必要になる条件**: ADRが増えて一覧性が落ちた場合は、`docs/adr/README.md` に索引を追加することを検討する。
