# 報酬設定・抽選・獲得台帳をサーバーへ集約する

## 背景と課題
報酬設定は端末内のデータベースに保存している。端末が故障してデータを読み出せなくなると、登録した報酬設定を失い、別の端末で復元できない。

端末の報酬設定・抽選とサーバーのポイント消費が分離しており、獲得した報酬を手元の台帳で管理している。通信切断後も当選結果を回収でき、複数端末でも重複当選・消費が起きない仕組みが必要。

## 検討した選択肢

- 設定と台帳だけをサーバーへ移し、抽選は端末に残す
- 設定・抽選・台帳をサーバーへ移し、消費と当選記録を同一トランザクションで確定する

## 決定
後者を採用する。抽選要求IDを送信前にDataStoreへ保存し、結果不明時は同じPOSTを再送する。再取得専用GETは作らない。サーバーは要求IDごとの確定レスポンスを保持する。

繰り返し不可は一括抽選中も1回だけ当選し、当選後の確率はハズレへ置換する。台帳は獲得時の名前・説明を保持し、使用済みになっても削除しない。

### 結果・トレードオフ

- ローカル報酬設定と既存の手元の台帳は移行しない。報酬Roomを撤去し、サーバーの残高・既存データは維持する。
- 抽選・使用・設定編集には通信が必要。保留抽選がある間は新しい抽選を開始しない。
- 設定のversionで編集競合を検出する。確率は0.01%単位の整数、合計100%以下とする。
- 旧購入テーブルは保持し、新テーブルをFlywayで追加する。全APIで所有者を検証し、テーブルのRLSも有効にする。
- チケット消費は抽選APIに集約し、旧消費APIは削除する。
